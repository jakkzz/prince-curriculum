# Phase 6 — A Real Product

**Duration:** 5 weeks
**Prerequisites:** Phase 5 gate passed.

## Why this phase exists

`questly` was a learning artifact. Phase 6 builds something **someone outside this course actually uses**. The point isn't the code — the point is the loop of finding users, hearing what they need, shipping, hearing what broke. That loop is the real skill.

## Learning objectives

By the end of this phase, the learner can:

1. Identify a real problem someone has, scope a minimum useful version, ship it.
2. Onboard ≥3 real users who aren't them, the mentor, or a parent.
3. Run a real product: handle support, triage bugs, ship updates.
4. Write a design doc that's read by someone who didn't help write it.
5. Add features they didn't think about in advance — files, email, rate limits, background jobs.
6. Write a post-mortem when something breaks.
7. Hold themselves to a quality bar even when no one's grading.

## Week structure

| Week | Topic | Output |
|------|-------|--------|
| 1 | Idea selection, design doc, scoping | DESIGN.md reviewed; users lined up |
| 2 | Build the MVP | Working, deployed, ugly |
| 3 | First users + iterate | 3 real users, first bug fixed |
| 4 | Adding "real" features | Email, files, background jobs, rate limits |
| 5 | Polish, retrospective, post-mortem | Shipped, written up, gate ready |

## What you build (idea catalog)

Pick **one**. Mentor approval required.

| Idea | Domain | Why it works |
|------|--------|--------------|
| Family chore tracker | household | Real users: siblings/parents. Hits auth, files, notifications. |
| Study group flashcards | education | Real users: classmates. Hits spaced repetition logic, sharing. |
| Sports club roster + drills | hobby | Real users: a coach + team. Hits roles, calendars. |
| School club budget tracker | clubs | Real users: club treasurer + members. Hits permissions, files. |
| Local-business booking page | entrepreneurial | Real users: an actual business. Hits public/private split. |
| Volunteer hour logger | non-profit | Real users: a real org. Hits exports, reports. |

**Bad ideas (mentor will veto):**
- "An app like Twitter." Too vague.
- "Anything with crypto." No.
- "A clone of an existing app." Boring and unmotivating.
- "Something hypothetical no one would use." Defeats the point.

## What the mentor watches for

- Does the design doc reflect real thinking, or is it a generic template?
- Did they actually deploy in Week 2, or did they polish for 3 weeks first?
- Do they have **real user feedback**, or are they guessing?
- Are they keeping the scope small enough to ship, or padding the feature list?
- When something broke, did they write it down?
