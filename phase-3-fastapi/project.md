# Phase 3 Project — `questly`

A small gamified habit/quest tracker API. Users register, log in, create quests, complete them, track XP and streaks.

## Why this domain

It's small enough to ship in 6 weeks, but it has enough relationships (users → quests → completions) to teach real schema design. And streak/XP logic gives space for non-trivial business logic.

## Deliverable

A public GitHub repo named `questly` with:

- A FastAPI app, dockerized.
- A Postgres schema managed by Alembic.
- JWT auth (access + refresh).
- ≥ 80% test coverage on the auth and quest modules.
- A README that lets a stranger run `docker compose up` and use the API.

## Endpoints

### Auth
- `POST /auth/register` — create a user.
- `POST /auth/login` — return access + refresh tokens.
- `POST /auth/refresh` — exchange refresh for new access token.
- `POST /auth/logout` — revoke current refresh token.
- `GET /auth/me` — current user.

### Quests
- `POST /quests` — create.
- `GET /quests` — list mine. Filters: `completed`, `since`, `tag`.
- `GET /quests/{id}` — get one. 403 if not yours.
- `PATCH /quests/{id}` — update title/description/xp_reward (not completion).
- `POST /quests/{id}/complete` — mark complete. Updates user XP and streak.
- `DELETE /quests/{id}` — delete.

### Stats
- `GET /stats/me` — total XP, current streak, longest streak, completions by day (last 30 days).

### System
- `GET /health` — always 200 if process alive.
- `GET /ready` — 200 only if DB reachable.

## Data model

```
users
├── id (PK)
├── email (unique, indexed)
├── hashed_password
├── created_at
└── deleted_at (nullable; soft delete)

quests
├── id (PK)
├── user_id (FK users)
├── title
├── description (nullable)
├── tag (nullable)
├── xp_reward (1..1000)
├── created_at
└── deleted_at (nullable)

completions
├── id (PK)
├── quest_id (FK quests)
├── user_id (FK users)         # denormalized for fast lookup
├── completed_at
└── xp_earned

refresh_tokens
├── id (PK)
├── user_id (FK users)
├── token_hash                  # store the hash, not the raw token
├── expires_at
├── revoked_at (nullable)
└── created_at
```

### Required indexes

- `users.email` (unique → implicit index)
- `quests.user_id`
- `quests(user_id, deleted_at)` for the "my active quests" query
- `completions(user_id, completed_at DESC)` for the stats query
- `refresh_tokens.token_hash`

Justify each one in `DESIGN.md`.

## Functional requirements

- [ ] All passwords stored hashed (argon2id). Verify with the mentor.
- [ ] JWT access tokens expire in 15 min. Refresh tokens in 30 days.
- [ ] Refresh tokens are stored **hashed** in DB and can be revoked.
- [ ] Auth endpoints rate-limited to 5/min per IP.
- [ ] All endpoints that mutate require auth.
- [ ] All endpoints that read user data check `user_id` matches.
- [ ] Streaks computed correctly across timezone (use user's local day, store in UTC).
- [ ] Soft delete: deleted quests don't return from list but are recoverable.
- [ ] Pagination on `GET /quests` (limit/offset, max 100).
- [ ] Validation errors return 422 with field-level detail.
- [ ] Server errors return 500 without leaking internals.

## Non-functional requirements

- [ ] OpenAPI page at `/docs` works and has descriptions on every endpoint.
- [ ] `docker compose up` brings up API + DB from a clean clone.
- [ ] Alembic migrations apply cleanly on a fresh DB.
- [ ] At least one migration has been written, applied, and tested for downgrade.
- [ ] Structured (JSON) logs in production.
- [ ] No secrets in the repo. `.env.example` only.
- [ ] CI runs lint, type-check, tests on every PR. Green on main.
- [ ] `mypy --strict` clean on the `src/` tree.

## Common ways this goes wrong

- **JWT in the URL.** It's a token; URLs are logged. Headers only.
- **`hashed_password` stored… not hashed.** Watch the registration code carefully.
- **No DB transaction around "complete a quest + add XP."** Race condition waiting to happen.
- **Test database leaks between tests.** Use a fresh schema per test, or a transactional fixture.
- **AI-generated code.** It will show up in patterns the learner can't explain.

## Adversarial review

When the mentor reviews, they will try (and the learner should anticipate):

1. Register two users. Log in as A. Try to fetch user B's quests by ID. Should 404 or 403, never return them.
2. Modify a JWT payload to change the `sub` claim. Try to access protected endpoints. Should fail.
3. Hit `/auth/login` with wrong password 20 times in a row. Should be rate-limited.
4. Send a quest title that's 50,000 chars long. Should 422 with a useful message, not crash.
5. Send `xp_reward: -1`. Should 422.
6. Stop the DB container, hit `/ready`. Should 503 (not 200).
